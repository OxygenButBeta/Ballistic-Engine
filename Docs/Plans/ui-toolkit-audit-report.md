## CRITICAL (3)
- **[bug] :hover/:active/:focus styles never apply on interaction (cascade is never re-run on state change)**  
  `UI/Input/UIInputModule.cs:75` — The whole point of pseudo-class support is interactive restyling. The input module toggles the 'hover'/'active' classes on the element (UIInputModule.cs:65/75/91/104) but NOTHING re-runs the cascade afterward. The only callers of StyleSheet.Apply/ApplyStyles are UIDocument.Rebuild() (initial load) and a manual public ApplyStyles() (UIDocument.cs:138/147). So a rule like `.btn:hover { background-color: red }` parses, gets the right specificity, even matches once the class is present — but Matches() is only ever evaluated at load time, when the 'hover' class is absent. Result: hover/active/focus styling is dead on arrival. Confirmed by grep: no Restyle/dirty hook fires from AddToClassList/RemoveFromClassList.
  _verify:_ Confirmed. UIInputModule toggles the "hover"/"active" state classes via AddToClassList/RemoveFromClassList (UIInputModule.cs:65/75/91/104), but those methods (VisualElement.cs:140/146) are pure list mutations with no restyle/dirty hook. The cascade (StyleSheet.Apply, which matches :pseudo as those very state classes per Selector.cs:36) runs ONLY from UIDocument.ApplyStyles() (UIDocument.cs:144), which is called only from Rebuild() at load (line 138) and as a manual public method. Nothing re-runs the cascade when the class set changes at runtime, so :hover/:active/:focus rules — absent at load time — never apply on interaction. (Additional gap worth noting: even if re-run, the cascade only additively applies matching rules onto Style and never resets/reverts, so state styles couldn't cleanly revert on hover-out either — but the primary claim stands as stated.)

- **[bug] Cascade is purely additive — toggling state (or removing a class) never reverts to base style**  
  `UI/Style/StyleSheet.cs:87` — ApplyToElement only calls StyleApplier.ApplyInline for each MATCHED rule; it never resets the Style to defaults first and never tracks which properties a previously-matching rule had set. So even if the cascade WERE re-run on a hover-out, the :hover rule's background would persist because nothing clears it. CSS/UITK recompute the full resolved style from the set of currently-matching rules each restyle; here Style is a mutable accumulator. This makes correct dynamic restyling impossible without a full element rebuild, and also means calling ApplyStyles() twice (e.g. after adding dynamic rows, UIDocument.cs:144) re-stacks rules on already-styled elements rather than recomputing — idempotent only because the same values get re-written, but any state-dependent rule leaks.
  _verify:_ Core defect confirmed: ApplyToElement (StyleSheet.cs:87) only applies each matched rule's declarations onto the mutable el.Style with no reset-to-default and no tracking of which properties prior rules set. UI Style is created once per element (VisualElement.cs:91) and never reset; ApplyStyles() (UIDocument.cs:144) re-runs _sheet.Apply (purely additive) + re-asserts inline, so it re-stacks rather than recomputes. Removing a class then calling ApplyStyles() leaves the old rule's values in place — a real, exercisable leak. Minor correction to the stated case: the live hover-out scenario does NOT actually misbehave today because UIInputModule (UpdateHover) adds/removes the 'hover' class but never calls ApplyStyles on hover transitions — so the cascade is never re-run on state change at all (a related gap: :hover rules are effectively dead, applied only at Rebuild). Net: dynamic/state-dependent restyling is impossible without a full rebuild; the additive-accumulator design is a genuine architectural bug. Severity 'critical' is somewhat strong given no in-engine code path currently triggers the hover leak, but the design flaw and the public ApplyStyles class-removal leak are real.

- **[bug] USS state styling (:hover/:active/:disabled) never reverts — cascade is write-only with no Style reset**  
  `UI/Style/StyleSheet.cs:62 + UI/Style/Style.cs (no Reset) + UI/Input/UIInputModule.cs:65` — The core documented feature 'state styling in ported controllers — :hover/:active/selected toggled as classes' is broken.   _verify:_ Mechanism fully confirmed by source. (2) No revertible baseline — Style (UI/Style/Style.cs) has no Reset/clear; StyleApplier.ApplyInline/ApplyOne (UI/Style/StyleApplier.cs:22-124) only WRITE set properties onto the live Style; UIDocument.ApplyStyles (UIDocument.cs:144-150) re-runs the cascade without first resetting to defaults, so a value applied while a :hover rule matched stays baked after the class is removed. ## HIGH (19)
- **[correctness] Multi-font atlas: EnsureAtlas re-uploads slot 0 every frame when two different font families are used, and only the last-bound atlas is correct**  
  `BallisticEngine.DX12/UI/Dx12UIRenderer.cs:474` — EnsureAtlas supports exactly ONE atlas bound at slot 0 (acknowledged R3 limitation), but the failure mode is worse than 'one font only': because all text segments hard-bind slot 0 (DrawText line 241), and CloseSegment captures only the SrvSlot (=0) not WHICH atlas, two text elements in the SAME frame using different families both record segments pointing at slot 0. Whichever atlas was uploaded LAST (the last EnsureAtlas before Flush) is what slot 0 holds at draw time, so the first font's glyph quads sample the second font's atlas with the first font's UVs -> garbage glyphs. Additionally the EnsureAtlas guard `atlas == uploadedAtlas && UIFonts.Version == uploadedFontVersion` (line 476) re-uploads (full CreateCommittedResource + CopyTextureRegion + synchronous ExecuteUpload) every time the bound atlas differs from the cached one, so alternating two fonts within a frame triggers a synchronous GPU upload PER glyph run — a severe per-frame stall, not just incorrect output.

- **[robustness] SRV heap silently drops every texture past slot 255 — gradients/images vanish, not error**  
  `BallisticEngine.DX12/UI/Dx12UIRenderer.cs:575` — RegisterImage (575) and UploadRgba8Texture (591) both `return -1` once `srvCursor >= SrvHeapCapacity` (256). The callers DrawGradient (225) and DrawImage (309) then `return` and draw NOTHING — no log, no fallback. Because slot 0 is the atlas and slots start at 1, only 255 transient textures fit per frame, and CRUCIALLY each DrawGradient bakes a FRESH ramp every call (no dedup/cache), so a UI with 256+ gradient draws (common: many buttons/progress bars with gradient backgrounds, or repeated list rows) silently loses everything past the budget. The element just disappears with no diagnostic. Needs at least a one-time warning and ideally ramp dedup so identical gradients share a slot.

- **[perf] Per-frame GPU+GC churn: every gradient and image allocates a new committed resource + full ExecuteUpload device stall EVERY frame**  
  `BallisticEngine.DX12/UI/Dx12UIRenderer.cs:531` — DrawGradient → BakeGradientRamp allocates `new byte[256*4]` (line 534) AND a brand-new default-heap committed texture + a new upload-heap committed buffer (UploadRgba8TextureToSlot, 599/610) on EVERY call EVERY frame; Begin() disposes them all next frame (195). DrawImage's RegisterImage doesn't allocate a texture but still consumes a slot. Worse, each upload goes through dev.ExecuteUpload which Signals+blocks on a fence (Dx12Device.cs:193-199): a UI with N gradients does N full GPU round-trips per frame plus N committed-resource create/destroy pairs — committed-resource creation is one of the most expensive D3D12 calls and is happening in the render hot path, plus steady-state GC pressure from the byte[] and resource wrappers. A persistent ring/atlas of ramps (keyed by stop hash) and a reused staging buffer would remove essentially all of it; the VB/IB path already does exactly this (EnsureBuffers grows-and-reuses) — the texture path regressed from that discipline.
  _verify:_ Accurate as a perf defect. One headline imprecision: only gradients allocate a new committed resource each frame; DrawImage/RegisterImage (line 573) creates only an SRV descriptor (consumes a slot), no resource — though the finding's body already states this correctly. Verified: DrawGradient (220) -> BakeGradientRamp (531) allocates new byte[256*4] (534) + default-heap committed texture (599) + upload-heap buffer (610) with no stop-hash cache (grep shows no gradientCache/rampCache); transientTextures disposed every Begin() (195); ExecuteUpload (Dx12Device.cs 187-200) Signals+blocks WaitOne per call -> N gradients = N round-trips/frame; VB/IB path (EnsureBuffers 730) does grow-and-reuse, confirming the texture path lacks that discipline.

- **[bug] Label measure func does NOT re-measure on font-size / font-family / letter-spacing change — stale text size**  
  `UI/Elements/Label.cs:17 (and UI/Style/Style.cs:118,131,132)` — The Yoga measure callback (Label.InstallMeasure) reads Style.FontSize, Style.FontFamily and Style.LetterSpacing every time it runs, but Yoga CACHES the measure result and only re-invokes the callback when the node is marked dirty. The ONLY thing that marks the measured node dirty is the Text setter (`Text { set { ...; Layout.MarkDirtyIfMeasured(); } }`). FontSize / FontFamily / LetterSpacing are plain public fields on Style (no setter logic at all), so assigning them — e.g. a USS rule or a :hover class that changes `font-size`, or the StyleApplier writing `font-size`/`letter-spacing`/`font-family` — does NOT dirty the Yoga node. Result: the label keeps its OLD intrinsic width/height until the text string also happens to change. This is exactly the 'does it re-measure on font/size/letterSpacing change, not just text?' failure: it re-measures only on text. Unity's TextElement invalidates layout (IncrementVersion / measure) on any of these. Fix: route FontSize/FontFamily/LetterSpacing through property setters that call Layout.MarkDirtyIfMeasured() (and ideally also invalidate when UIFonts.Version changes — a font registered AFTER first layout never re-measures either).

- **[bug] Child (>), adjacent-sibling (+) and general-sibling (~) combinators silently downgraded to descendant**

  _verify:_ Confirmed accurate. StyleSheet.cs:110 drops '>', '+', '~' tokens (continue) and ParseSelector splits on whitespace only, so every combinator collapses into one descendant Chain. # Ballistic UI Toolkit — Gap Analysis to "UITK quality or better"

The confirmed-findings list is strong on *primitive-level* defects (clipping, SDF AA, measure invalidation, selector combinators, var(), per-frame GPU churn). ## 1. STYLING — biggest architectural debt

The findings nail the symptoms (no inheritance, additive-only cascade, dead `:hover`, no `var()`). But they describe these as separate bugs. **They are one root cause: there is no computed-style model.** `Style` is a live mutable accumulator written directly by `StyleApplier`; there is no notion of "the set of matching rules → resolved style." Until that exists, every state/inheritance/transition fix is a hack on a broken base.

|---|---|---|---|
| **Resolved-style architecture** (matched-rule-set → recompute, revertible baseline, specificity+`!important` tiers) | The single fix that makes `:hover` revert, re-cascade-on-state, inheritance, and transitions all *possible*. Everything else in this section is blocked on it. | arch/critical | **L** |
| Re-run cascade on class/state change (hook `AddToClassList`/`RemoveFromClassList` → mark element restyle-dirty) | Without it `:hover/:active/:focus` are dead on arrival (findings confirm). | critical | M (after arch) |
| Property inheritance (color/font-*/letter-spacing/text-align/visibility/white-space) | "Set typography once on the root" is the #1 Claude-design pattern; today every Label resets to engine defaults. | high | M |

| Real combinators `>` `+` `~` (not downgrade-to-descendant) | Current behavior is *wrong matches*, not missing coverage — applies styles to elements it must never touch. | high | M |
| `!important` parsing + precedence tier | Today it corrupts the value to 0/transparent (rides into the parser). | medium | S |
| Multiple stylesheets per document + `<ui:Style src>` + `@import` | Real designs split base/theme/component sheets; only one `_sheet` is wired. | medium | M |
| Cascade perf: rule bucketing by class/type/name + parsed-declaration cache (kill per-element List+sort+re-tokenize) | Once hover re-cascade is correct, doing the current O(elements×rules) walk per pointer-move is untenable. | medium | M |
