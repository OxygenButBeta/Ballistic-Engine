Ballistic Engine

A custom, AI-native game engine written in modern C# / .NET 9. Unity-familiar idioms, a from-scratch DX12 + DXR renderer with real-time Lumen-class global illumination, and a complete headless agent surface so the whole engine is operable from the command line.

Language C# / .NET 9 Renderer DirectX 12 + DXR Editor ImGui Physics BepuPhysics 2 Platform Windows / PC

Ballistic Engine deliberately mirrors Unity's mental model — Entity + Behaviour, an AssetDatabase with .meta sidecars, an edit/play split, attribute-driven inspectors — so anyone who has used Unity is immediately productive. Under the hood it is its own thing: a clustered-deferred DX12 renderer with ray-traced GI and reflections, a server-authoritative networking stack, a code-driven animation system, and a first-class headless operability layer (the bal CLI, an MCP server, and a live editor pipe) that lets both humans and AI agents drive every part of the engine without a GUI.

Getting Started #

Build & run

The solution is BallisticEngine.slnx (five projects). From the repo root:

shell# Build everything
dotnet build BallisticEngine.slnx

# Launch the ImGui editor on the bundled sample project
dotnet run --project BallisticEngine.Editor

# Launch the standalone player (no editor)
dotnet run --project BallisticEngine.Runtime

# Point either at a different project folder:
dotnet run --project BallisticEngine.Editor  C:\path\to\MyProject

If no project path is given, both default to the repo's SampleProject.

GotchaAfter changing engine code, rebuild the root BallisticEngine library (not just the exe project) or the executable links a stale DLL.

Your first script

Game code is just .cs files anywhere under your project's Assets/ folder — exactly like Unity. The file name must match the class name. Create Assets/Spinner.cs:

csharpusing BallisticEngine;

// File: Spinner.cs  →  class name MUST be Spinner
public class Spinner : Behaviour {
    [Header("Rotation")]
    [Range(0f, 360f)]
    public float DegreesPerSecond = 90f;

    // In a GAME assembly, lifecycle overrides must be `protected` (not protected internal).
    protected override void Tick(in float delta) {
        transform.Rotation *= Quaternion.FromAxisAngle(
            Vector3.UnitY, Mathf.Deg2Rad * DegreesPerSecond * delta);
    }
}

Alt-tab back to the editor (or press Ctrl+R) and it compiles automatically. Spinner now appears in the Add Component menu and the DegreesPerSecond slider shows in the Inspector — zero wiring. Drag the .cs tile onto an entity row to attach it. Press Space to play and watch it spin.

The one rule that bites everyoneIn game assemblies, lifecycle overrides (Tick, OnBegin, FixedTick, …) must be declared protected, never protected internal. That's a C# cross-assembly override rule — the engine declares them protected internal, but your code can only widen to protected.

The General Flow #

From process launch to a rendered frame — the path data takes through the engine.

1 · Boot

A host (the player or the editor) hands its window and graphics device to EngineBootstrap, which wires the singletons: the physics world, the renderer, the AssetDatabase, audio, and networking are all injected behind interfaces so layers stay decoupled. Game scripts are compiled into Library/ScriptAssemblies/GameScripts.dll and loaded into a collectible context before the component registry is built, so your Behaviour types are known to the deserializer.

2 · Load the scene

The project's startup scene (ScenesInBuild[0]) is read from YAML. SceneSerializer reflects each component's members back from text, resolves asset references (guid:… → real Mesh/Material via the AssetDatabase), and rebuilds the transform hierarchy. OnAttach fires on every component in both edit and play mode — this is where rendering and audio register themselves.

3 · Edit vs. Play

The engine has a hard edit/play split, just like Unity:

ModeWhat runs
EditOnly OnAttach/OnDetach and gizmo drawing. No scripts tick, no physics. You arrange the scene.
Play (Space in editor)StartPlay() snapshots the scene to YAML, then fires the full lifecycle: OnEnabled → OnBegin → per-frame Tick / fixed-step FixedTick. StopPlay() restores the snapshot so play never mutates your edit scene.

4 · The frame loop

Each frame, in order:

  1. Fixed steps — the physics accumulator runs zero-or-more 60 Hz steps; FixedTick fires before each, then Bepu solves, then poses are written back and contact events (OnCollisionEnter…) dispatch.
  2. Tick — every enabled Behaviour.Tick(delta) runs (gameplay, input handling, animation drive).
  3. Coroutines & jobs — scheduled jobs flush, coroutines resume.
  4. Render — the renderer reads SceneManager.RenderCamera, culls, and draws the frame (see below).
  5. Present — the swapchain flips. The editor's order is UI-build → scene-render → present so gizmo drags don't lag a frame.

5 · The render pipeline

The DX12 backend runs a fixed, well-defined frame shape (TAA is the anti-aliasing — there is no MSAA path):

frame shapecull → cascaded shadows (cached) → z-prepass → SSAO
   → opaque (clustered deferred) → sky → transparent
   → SSGI → SSR → volumetric fog → TAA / FSR
   → auto-exposure meter → bloom → color grade → composite

Off-screen geometry is culled on the GPU (compute frustum + Hi-Z occlusion), whole-mesh scenes are drawn with ExecuteIndirect, and global illumination is traced against the scene's ray-tracing acceleration structure (DXR), falling back to screen-space GI on hardware without RT. See Rendering & Volumes for the full feature set.

Headless tooEvery step above runs without a window via the bal CLI: bal simulate runs the real fixed-step + script loop, and bal render runs the real render pipeline to a deterministic image. The agent surface is not a mock — it's the engine.

Architecture & Layers #

The engine enforces strict, grep-auditable layering. Each layer may only reference the ones above it — this keeps the renderer swappable and the core portable.

LayerMay useMust NOT use
Shared/, ToolKit/BCL onlyeverything else
Abstraction/Shared, OpenTK.MathematicsGPU calls, file formats
Engine/Abstraction, SharedAssimp/Stb/Magick, asset file I/O
Physics/Abstraction, BepuPhysicsGPU, asset libs, Engine internals
AssetPipeline/everything + import libsdirect GPU upload (goes via RenderAsset)
BallisticEngine.DX12/Abstraction, Engine typesasset import libraries

Dependency injection at the seams

The big subsystems are interfaces resolved once at bootstrap, never reached for directly from gameplay:

  • IPhysicsWorld — only Physics/Bepu/ references BepuPhysics; the rest of the engine talks to the interface. The static Physics facade is the public face.
  • IRenderer / the DX12 backend — engine code emits render data; the backend consumes it.
  • Asset libraries (Assimp, StbImage, Magick) live only in AssetPipeline/.
  • BCL-only facades like Profiler and JobSystem are no-ops until a backend is installed.
Why this matters to youYou never new a physics world or a renderer. You call the static facades (Physics.Raycast, Input.IsKeyDown, AssetDatabase.Load<T>) and write Behaviour subclasses. The wiring is the engine's job.

Object Model #

Everything in a scene is an Entity with a Transform and a list of Behaviour components. If you've used Unity, this is the GameObject / MonoBehaviour pattern.

The hierarchy of types

type treeBObject              // identity (InstanceId) + Name; base of everything
 ├─ Entity           // transform + components (the "GameObject")
 └─ Component
     └─ Behaviour     // attachable, has the full lifecycle — you subclass this
         ├─ Transform          // always present on every entity
         ├─ StaticMeshRenderer
         ├─ Rigidbody, BoxCollider, …
         └─ YourScript          // your gameplay code

SceneBehaviour      // scene-wide component (Skybox, lighting, GameMode)

Working with entities & components

csharp// Create an entity and build it up
var player = Entity.Instantiate("Player");
var rb     = player.AddComponent<Rigidbody>();
var col    = player.AddComponent<CapsuleCollider>();

// Look components up (the lookups also exist directly on Behaviour)
var renderer = player.GetComponent<StaticMeshRenderer>();
if (player.TryGetComponent<Rigidbody>(out var body)) body.AddForce(Vector3.UnitY * 10);

var gun  = player.GetComponentInChildren<Weapon>();
var root = player.GetComponentInParent<CharacterRoot>();

// Tags, layers, activation
player.Tag = "Player";
if (other.CompareTag("Enemy")) { … }
player.SetActive(false);  // fires OnDisabled in play mode

Component Lifecycle #

Override these on your Behaviour to hook into the engine. The split between "both modes" and "play only" is the thing to internalize.

MethodWhenUse it for
OnAttach()Both edit & play — when added to an entity / scene loadsRegister with the renderer or audio. Anything that must show in the edit viewport.
OnDetach()Both — when removed / scene clearsUnregister; mirror of OnAttach.
OnBegin()Play, once, first time activeOne-time init (Unity's Start). Cache components here.
OnEnabled() / OnDisabled()Play, each (de)activationPaired enable/disable logic.
Tick(in float delta)Play, every framePer-frame gameplay, input polling, animation drive.
FixedTick(in float delta)Play, fixed 60 HzPhysics input — forces, velocities, impulses.
OnCollisionEnter/Stay/Exit(Collision)Play, after each fixed stepReact to solid contacts.
OnTriggerEnter/Stay/Exit(Collider)Play, after each fixed stepReact to trigger overlaps.
OnDrawGizmos(IGizmos)Editor scene view, every frameAlways-on debug visualization.
OnDrawGizmosSelected(IGizmos)Editor, when selectedSelection-only handles & ranges.
Register in OnAttach, not OnEnabledOnEnabled is play-only. If you register your renderer there, the editor viewport goes black in edit mode. Render and audio registration must live in OnAttach.
Fault isolationA script exception never crashes the engine — every dispatch site is guarded, logs an Assets/…cs:line stack, and a callback that throws 3× in a row auto-disables that component. Spawning and destroying entities from inside Tick is legal (iteration is snapshotted).

A complete component

csharpusing BallisticEngine;

public class PlayerController : Behaviour {
    [Header("Movement")] [Range(0f, 15f)]
    public float MoveSpeed = 5f;
    [Range(0f, 10f)]
    public float JumpImpulse = 5f;

    Rigidbody rb;

    protected override void OnBegin() {
        rb = GetComponent<Rigidbody>() ?? entity.AddComponent<Rigidbody>();
    }

    protected override void FixedTick(in float dt) {
        float x = (Input.IsKeyDown(Keys.D) ? 1 : 0) - (Input.IsKeyDown(Keys.A) ? 1 : 0);
        rb.Velocity = new Vector3(x * MoveSpeed, rb.Velocity.Y, 0);

        if (Input.IsKeyPressed(Keys.Space) && IsGrounded())
            rb.AddImpulse(Vector3.UnitY * JumpImpulse);
    }

    protected override void OnCollisionEnter(Collision c) {
        if (c.Entity.CompareTag("Hazard")) Debug.Log("Ouch!");
    }

    bool IsGrounded() => Physics.Raycast(transform.WorldPosition, Vector3.Down, out _, 1.1f);
}

Scenes & Serialization #

A .scene is a human-readable YAML file. Components serialize by reflection — every public read/write property and public field round-trips, no boilerplate.

The format

yamlversion: 1
name: MainScene
sceneComponents:           # scene-wide SceneBehaviours
  - type: ProceduralSky
    id: 6fa759e0556a44a0bdaa7400837a3a76
    enabled: true
    members: { exposure: 1, airDensity: 1 }
entities:
  - id: 362ce5ee44d943e586b4cd730433ffa5   # file-local; wires parents
    name: Player
    tag: Player
    transform:
      position: { x: 0, y: 1, z: 0 }
      rotation: { x: 0, y: 0, z: 0, w: 1 }
      scale:    { x: 1, y: 1, z: 1 }
    components:
      - type: StaticMeshRenderer
        members:
          sharedMesh: guid:1373de82334d41269f8bb0028d678db9
          sharedMaterial: guid:c13c6e1f320940ce81adcdcbda99e5b7
      - type: BoxCollider
        members: { size: { x: 2, y: 2, z: 2 } }

Defaults are omitted for clean diffs (isActive: true, layer: 0, tag: Untagged, parent: null never appear). Asset members serialize as guid:… (rename-proof) or as an Assets/… path. Component ids are preserved across save/load so editor selection and event listeners survive a reload.

Loading & querying in code

csharpSceneSerializer.Load("Assets/Scenes/Main.scene");
Scene scene = SceneManager.GetCurrentScene();

foreach (Entity e in scene.Entities)
    if (e.TryGetComponent<StaticMeshRenderer>(out var r))
        Debug.Log($"{e.Name} → {r.SharedMesh?.Name}");
Two members opt out[NotSerialized] hides a public member from both YAML and the inspector (runtime-only state like Rigidbody.Velocity). [HideInInspector] hides it from the inspector only — it still serializes.

Game Scripting #

Drop .cs files under Assets/. The engine compiles them into a hot-reloadable assembly and discovers your components by reflection — no registration, no manifest.

How it compiles

All game .cs files under Assets/ build (via dotnet build) into Library/ScriptAssemblies/GameScripts.dll, loaded into a collectible AssemblyLoadContext. A Scripts.csproj is generated at the project root so your IDE opens game code as a real project with engine references. While its "Generated by Ballistic Engine" marker comment is present the engine manages it; delete the marker to take ownership (add NuGet packages, change settings) and the engine builds it as-is.

Hot reload live, even during play

  • Editor: automatic when you alt-tab back to the editor after editing in your IDE, plus manual Ctrl+R / File ▸ Rebuild Scripts.
  • Compile-first: on errors nothing changes — they appear in the Console as Assets/…(line,col): error CSxxxx. On success the scene snapshots to YAML → unloads the old DLL → loads the new one → re-deserializes.
  • Reload does not stop play. The live scene (play-mode spawns and mutated values) round-trips through YAML and the lifecycle restarts on the new types. The pre-play snapshot is untouched, so Stop still returns to the edit scene.
  • Compile errors block running, not editing — the Play button disables with the reason in its tooltip; the standalone player exits code 1.

Discovery rules

  • File name == class name (Unity's rule). Spinner.cs must contain class Spinner. Dragging the .cs tile onto an entity adds that component; onto empty hierarchy space creates an entity with it.
  • Public read/write properties and public fields serialize and appear in the inspector.
  • Lifecycle overrides must be protected in game code (see the getting-started gotcha).

Asset Pipeline #

A Unity-style, GUID-based asset system. Sources live in Assets/ with .meta sidecars; the importer bakes binary artifacts into a regenerable Library/ cache.

Project layout

foldersMyProject/
 ├─ project.json              # identity, scenes-in-build, player settings
 ├─ Scripts.csproj            # engine-generated; your game code project
 ├─ Assets/                   # SOURCES + .meta GUID sidecars
 │   ├─ Models/Car.fbx  +  Car.fbx.meta
 │   ├─ Models/Car_Materials/*.mat      # auto-generated on import
 │   ├─ Scenes/Main.scene
 │   └─ Spinner.cs            # game scripts live anywhere under Assets/
 └─ Library/                  # gitignored, regenerable
     ├─ Artifacts/*.bmesh,*.btex   # compiled binary assets
     ├─ ArtifactDB.json  +  guidmap.json
     └─ ScriptAssemblies/GameScripts.dll

Loading assets

csharpMesh     mesh = AssetDatabase.Load<Mesh>("Assets/Models/Car.fbx");
Material mat  = AssetDatabase.Load<Material>("Assets/Materials/Paint.mat");

// Either reference form works (path is human-readable; guid is rename-proof):
var a = AssetDatabase.LoadRef<Material>("Assets/Materials/Paint.mat");
var b = AssetDatabase.LoadRef<Material>("guid:c13c6e1f320940ce81adcdcbda99e5b7");

Load<T> caches by GUID (never loads twice) and never throws — on a missing or broken asset it logs and returns null (materials substitute fallback textures). See the AssetDatabase reference.

Importers & native formats

Source models/textures import to binary artifacts; several asset types are plain text and ship directly:

FormatWhat it is
.matMaterial — shader ref + texture slots (Diffuse/Normal/Metallic/Roughness/AO/Emissive) + PBR factors. JSON.
.shader / .glslShader program (vertex + fragment refs) and raw GLSL source.
.cubemapSkybox — six faces or an equirect panorama. JSON.
.volumeA post-processing VolumeProfile — a list of VolumeComponent overrides. JSON.

The ModelImporter merges a model into one submesh per material, generates a sibling _Materials/ folder, auto-binds textures by filename convention (Megascans/Substance packs), and fixes FBX cm→m units. The TextureImporter BC-compresses with mips (BC1/BC3/BC5). Loading any image as a Texture3D builds an equirect cubemap. There's also a full Unity package importer (.unitypackage → .scene).

Prefabs #

A prefab is a reusable entity blueprint — a captured subtree stored as a .prefab asset. Instances stay linked to the asset and track per-member overrides.

Workflow in the editor

  • Create — build an entity, select it, right-click ▸ Create Prefab. It saves a .prefab next to the current Asset Browser folder; the instance gets a prefab-root badge.
  • Instantiate — drag the .prefab tile onto the Hierarchy.
  • Override — edit any member on an instance; overridden members are marked. Right-click ▸ Apply to Prefab pushes it to the asset, or Revert discards it.
  • Break / Apply All / Revert All — unlink the instance, or push/discard every override at once.

From code

csharpPrefabAsset prefab = AssetDatabase.Load<PrefabAsset>("Assets/Props/Crate.prefab");

Entity a = prefab.Instantiate();                                    // at origin
Entity b = prefab.Instantiate(new Vector3(0,1,0), Quaternion.Identity);
Entity c = prefab.Instantiate(parentTransform);                     // as a child

Input #

A static facade for keyboard, mouse, and Xbox-style gamepads. A master gate keeps editor edits from leaking into play.

csharpprotected override void Tick(in float dt) {
    // Keyboard
    if (Input.IsKeyDown(Keys.W))    transform.Position += transform.Forward * 5 * dt;
    if (Input.IsKeyPressed(Keys.Space)) Jump();          // true for one frame

    // Mouse
    Vector2 look = Input.MouseDelta;
    if (Input.IsMouseButtonPressed(MouseButton.Left)) Fire();

    // Gamepad (player 0)
    Vector2 move = Input.GetLeftStick();
    if (Input.IsGamepadButtonPressed(GamepadButton.A)) Jump();
}

IsKeyDown(Keys) / IsKeyPressed(Keys)Held this frame / newly pressed this frame.
IsMouseButtonDown / IsMouseButtonPressed(MouseButton)Held / newly pressed.
MousePosition / MouseDelta / ScrollDeltaVector2 screen pos, per-frame motion, wheel.

Enums: Keys, MouseButton, GamepadButton (A/B/X/Y, bumpers, D-pad, stick presses…), GamepadAxis (LeftX/Y, RightX/Y, triggers).

Physics #

BepuPhysics 2 behind the IPhysicsWorld interface. Add a Rigidbody + a collider, then drive it with forces in FixedTick. Runs in play mode at a fixed 60 Hz.

Bodies & colliders

A collider on an entity with a Rigidbody compounds into that body; a collider without one becomes static level geometry. Primitive colliders auto-fit to the render mesh on add.

csharpvar rb  = entity.AddComponent<Rigidbody>();
rb.Mass = 2f;  rb.UseGravity = true;
var col = entity.AddComponent<CapsuleCollider>();
col.Radius = 0.3f;  col.Height = 1.8f;

protected override void FixedTick(in float dt) {
    rb.AddForce(Vector3.UnitY * 50);            // continuous force (N)
    rb.AddImpulse(dir * 5);                     // instantaneous (kg·m/s)
    rb.Velocity = new Vector3(vx, rb.Velocity.Y, vz);
}

Collider types: BoxCollider (Size), SphereCollider (Radius), CapsuleCollider (Radius, Height), MeshCollider (concave, static-only, uses the entity's mesh by default). All share Center, Friction, Bounciness, IsTrigger.

Raycasts & queries

csharpif (Physics.Raycast(origin, Vector3.Down, out RaycastHit hit, 100f)) {
    Debug.Log($"Hit {hit.Entity.Name} at {hit.Point}, n={hit.Normal}");
}
Physics.SphereCast(origin, 0.5f, dir, out hit);
List<Collider> near = Physics.OverlapSphere(center, 3f);

Triggers & collisions

csharpprotected override void OnCollisionEnter(Collision c) { /* c.Entity, c.Point, c.Normal, c.Rigidbody */ }
protected override void OnTriggerEnter(Collider other) { /* other.IsTrigger overlap */ }

Joints & vehicles

Constraints: BallSocketJoint, HingeJoint (Axis), FixedJoint, SpringJoint (TargetDistance), SliderJoint (Axis) — set ConnectedBody (null = world anchor), Anchor, Frequency, DampingRatio. An arcade VehicleController + WheelCollider drive a chassis rigidbody with suspension, gearbox, steering, downforce and anti-roll.

GotchasMesh collision is one-sided (solid from the rendered front face). Bepu has no restitution — bounce is modelled with soft contact springs. World scale is baked into shapes at body creation; scaling during play won't resize. See the Rigidbody & Colliders reference for every member.

Animation #

GPU-skinned skeletal animation with two playback styles: a simple Animator (one clip + crossfade) and a code-driven AnimancerComponent (mixers, blend spaces, root motion, retargeting).

Simple clip playback

csharpvar anim = entity.AddComponent<Animator>();

Rendering & Volumes #

The DX12 + DXR backend is feature-complete with Lumen-class GI. You don't talk to it directly — you place lights, assign materials, and tune the look through Volumes (Unity HDRP-style stacked post-processing).

The Volume framework

A Volume is a Behaviour (global, or a local box with Priority / Weight / BlendDistance) that points at a VolumeProfile (.volume asset). Each profile holds VolumeComponents whose parameters override the engine defaults. The VolumeManager blends every active volume each frame by distance and priority; the renderer reads the blended stack.

workflowVolume (entity)  →  VolumeProfile (.volume asset)  →  VolumeComponents
                                                         (Bloom, Exposure,
                                                          GlobalIllumination, …)

In the editor: add a Volume component, assign or create a profile, then toggle component overrides inline. Defaults mirror the engine's so a no-volume scene looks identical.

The post-FX you can tune

Networking #

A server-authoritative replication framework: prediction & reconciliation, lag compensation, interest management, and zero-reflection state replication via source generation. LiteNetLib transport, loopback for single-player.

Networked components

Subclass NetworkBehaviour, mark replicated state with [Networked], and expose RPCs with [Rpc]. The source generator writes the (de)serialization — no reflection in the hot path.

csharppublic class PlayerPawn : NetworkBehaviour {
    [Networked] public Vector3 Position { get; set; }
    [Networked] public float Health { get; set; }

    [Rpc(RpcTarget.Server)]
    public void Fire(Vector3 dir) {
        if (!IsOwner) return;                      // owner-gated
        Network.LagCompensatedRaycast(origin, dir, Network.RenderTick, this, out var hit);
    }

    protected override void NetworkTick() {
        if (HasInputAuthority) Position += Input() * speed;  // predicted
    }
    protected override void OnStateApplied() => transform.WorldPosition = Position;

    [OnChanged(nameof(Health))] void HpChanged() => bar.Set(Health);
}

Roles & bring-up

Role queries on every networked component: IsOwner, HasStateAuthority, HasInputAuthority, IsProxy, IsAutonomousProxy, IsSimulatedProxy. Net-strand callbacks: OnSpawned, OnStartServer/Client/LocalPlayer, OnOwnershipChanged, OnInterestLost/Gained.

csharpNetwork.StartHost();                              // single-player = loopback, same code path
Network.StartServer(new LiteNetLibTransport());
Network.StartClient(new LiteNetLibTransport());
NetworkObject obj = Network.Spawn(entity, owner);

RPC targets: Server, Clients, All, Owner. State [Networked] supports opt-in quantization (Min/Max/Bits).

An opt-in, Unreal-style layer on top of Entity/Behaviour. It activates only when a scene declares a GameMode — otherwise the engine behaves exactly as before, byte-identical.

Jobs & Threading #

A frame-scoped parallel-for facade for per-frame CPU bulk work (animation, culling, particles). Not for background I/O, not for GPU calls.

Coroutines & Async #

Two interoperating styles — modern async/await awaiters (preferred) and classic Unity-style IEnumerator yields. Both resume on the main thread.

MCP & Live Control #

Beyond the one-shot CLI, the engine exposes the running editor to agents two ways: a Model-Context-Protocol server and a raw named pipe. Every mutation pushes undo first and marks the viewport dirty — remote edits behave exactly like human edits.

The named pipe

The editor listens on \\.\pipe\BallisticEditor, newline-delimited JSON: {id, method, params} → {id, result|error}. The pipe thread is engine-owned and survives script hot-reload. Methods (also help lists them):

editor.status, scene.describe / save / open, entity.get / create / delete, component.add / remove / set, scene.component.add / set, select, play.start / stop / pause / step, undo / redo, screenshot, console.tail, scripts.rebuild, editor.frame, editor.refresh, unity.import.

The MCP server

BallisticEngine.Mcp is a stdio MCP server wrapping the pipe in ~16 task-level tools an agent can call directly — editor_status, scene_describe, entity_create, component_set, play_control, scene_open, editor_screenshot, scripts_rebuild, scene_query, scene_gbuffer, and more. It connects lazily and auto-reconnects, so you can start it before or after the editor.

Three layers, by preferenceCLI (headless, no editor, most flexible) → MCP (lightweight tools, editor keeps the scene hot) → pipe (lowest-level, stateful multi-step workflows). They share the same underlying verb set.

Building a Player #

The Build panel (or BuildPipeline in code) produces a single self-contained Windows executable with your data baked in.

It compiles scripts (error-checked), refreshes & writes the asset GUID map, publishes the Runtime exe, renames it to the product name, and copies only the shippable data into Data/ — text assets (.scene, .mat, .shader, .volume, .prefab) plus the binary Library/ artifacts. Source models/textures/scripts are not shipped.

csharpvar result = BuildPipeline.Build(new BuildPipeline.Options {
    Project          = project,
    OutputDir        = @"C:\Build",
    ScenesInBuild    = new[] { "Assets/Scenes/Main.scene" },
    Configuration    = "Release",
    RuntimeIdentifier= "win-x64",
    SelfContained    = true,
});
if (result.Success) Console.WriteLine(result.ExePath);

Player settings (product/company/version, .ico icon, window mode & resolution) live in project.json under player and become the exe's metadata.
